# 映射规范：`hash-design/v2`

[English](mapping.md) · [返回 README](../README.zh-CN.md)

本页说明一个 256 位哈希如何变成一个设计方向。在 `hash-design/v2` 里，**哈希本身就是方向**：没有可供挑选的风格库、流派或分支。每个字节驱动一个设计参数（或按位拆成两个）：要么是连续值（色相、明度、比例、尺寸、时长），要么是一张短小原语列表里的下标，这些原语可以自由组合。这里的全部内容都实现在 [`packages/core/src/hash.ts`](../packages/core/src/hash.ts)、[`packages/core/src/mapping.ts`](../packages/core/src/mapping.ts) 和 [`packages/core/src/palette.ts`](../packages/core/src/palette.ts) 中，并由 `packages/core/test/mapping.test.ts` 覆盖。

## 1. 哈希从哪里来

| 模式             | 来源                                                           | `roll.json` 中的 `source` 字段 |
| ---------------- | -------------------------------------------------------------- | ------------------------------ |
| 真实使用（默认） | `sha256(crypto.getRandomValues(32 字节))`，即操作系统的 CSPRNG | `system-random`                |
| 示例和测试       | `sha256("hash-design/v2:<seed>:<index>")`                      | `seed:<seed>`                  |
| 仅限库调用方     | `roll({ hashes: [...] })`，哈希由你提供                        | `provided-hashes`              |

`seed` 的存在是为了让示例和测试可复现。Skill、MCP prompt 和 server instructions 都会告诉 Agent：真实工作中永远不要传 seed。

## 2. N 个方向

一次掷 N 个（1–12，默认 5）就是 N 个哈希逐个映射。每个设计只取决于它自己的哈希和约束：同一次掷骰里的设计之间没有任何共享，没有探测、没有去重，也没有会被用完的池子。一个设计的 **ref 就是它的 64 位十六进制哈希**，所以任何一个设计都可以单独用 `get_brief` / `hash-design brief <hash>` 重建。

带 seed 的掷骰前缀稳定：第 _i_ 个设计永远是 `sha256("hash-design/v2:<seed>:<i>")`，与 N 无关，所以 `--count 3` 得到的就是 `--count 12` 的前三个。

N 在哪里设：MCP 里是 `count`，CLI 里是 `--count`/`-n`，库里是 `DEFAULT_COUNT` / `MAX_COUNT`，Skill 从用户的话里读（“3 个方向”、`/hash-design 3`）。12 是产品上限，不是算法限制：每个方向都要单独写一份 brief、单独渲染一个独立预览，对比页的数字键也只能聚焦前九个。约束不会降低上限，因为约束只塑造每个设计，不会删掉候选。

同一次掷骰里的两个方向，差别就是两个随机哈希的差别：每个字节都独立。没有任何机制强行把它们拉开；每个字节有 256 个取值、参数有几十个，两个设计要完全相同，除非两个哈希完全相同。

## 3. 字节 → 参数

一个哈希有 32 字节，`b0` … `b31`。`hash-design/v2` 按下表读取（`mapping.ts` 中的 `BYTE_MAP`；同样的规则会连同十六进制值、算式和结果打印在每份 brief 的映射过程里）。

| 字节 | 参数                 | 规则                                                                                                  |
| ---- | -------------------- | ----------------------------------------------------------------------------------------------------- |
| 0–1  | 色相                 | `uint16(b0, b1) / 65536 × 360°`（纸、墨和强调色的 OKLCH 色相）                                        |
| 2    | 深浅 · 纸的明度      | `b < 77` → 深色，L = 0.14 + b/76 × 0.12；否则浅色，L = 0.90 + (b − 77)/178 × 0.085                    |
| 3    | 纸的彩度             | `b/255 × 0.045`（0 = 中性纸色）                                                                       |
| 4    | 强调色彩度           | `0.07 + b/255 × 0.16`                                                                                 |
| 5    | 第二强调色的色相偏移 | 相对强调色 `30° + b/255 × 300°`                                                                       |
| 6    | 标题字体             | 标题字体池中 `b mod 98`                                                                               |
| 7    | 正文字体             | 正文字体池中 `b mod 62`                                                                               |
| 8    | 标题大小写 · 字重    | 大小写 `b mod 4`（原样、全大写、全小写、小型大写）；字重 = 该字体自带字重[`⌊b/4⌋ mod n`]              |
| 9    | 标题字距             | `−0.04 + b/255 × 0.24` em                                                                             |
| 10   | 字号比例             | `1.067 + b/255 × 0.551`（1.067 … 1.618）                                                              |
| 11   | 密度                 | `t = b/255`，映射到场景的范围内（§5）                                                                 |
| 12   | 栅格列数 · 列间距    | `3 + (b mod 10)` 列；列间距 = 单位 × (1 + `⌊b/10⌋ mod 4`)                                             |
| 13   | 文本块跨度 · 起始列  | 跨度取 `b & 15`，起始列取 `b >> 4`（公式见下）                                                        |
| 14   | 首屏高度             | 视口的 `45 + b/255 × 55` %                                                                            |
| 15   | 区块数 · 分隔方式    | `3 + (b mod 6)` 个区块；分隔方式 `⌊b/6⌋ mod 5`（细线、色带、编号、留白、方框）                        |
| 16   | 锚点主体 · 尺寸      | 主体 `b mod 8`；尺寸为宽度的 `25 + ⌊b/8⌋/31 × 75` %                                                   |
| 17   | 锚点位置 · 旋转      | 水平位置 x = `(b & 15)/15`；旋转 `((b >> 4) − 7.5)/7.5 × 8°`（取到 0.5°）                             |
| 18   | 母题形状 · 尺寸      | 形状 `b mod 12`；尺寸 = 单位 × (1 + `⌊b/12⌋ mod 8`)                                                   |
| 19   | 母题位置 · 角度      | 位置 `b mod 4`（页边、区块之间、锚点背后、列表与标题标记）；角度 `⌊b/4⌋ × 180/63°`                    |
| 20   | 圆角 · 边框          | 圆角 `[0, 0, 0, 0, 2, 4, 8, 16][b mod 8]` px；边框 `⌊b/8⌋ mod 4` px；线型 `⌊b/32⌋ mod 4`              |
| 21   | 阴影 · 材质          | 阴影 `[0, 0, 2, 6][b & 3]` px，硬阴影（无模糊）；材质 `(b >> 2) & 3`；不透明度 `3 + (b >> 4) × 0.6` % |
| 22   | 动效属性 · 时长      | 属性 `⌊b/64⌋`（透明度、位移、裁切擦除、颜色）；时长 `(b mod 64)/63 × 600` ms                          |
| 23   | 缓动                 | `b < 32` → `steps(2 + b mod 6, end)`；否则由各位组成 `cubic-bezier`（见下）                           |
| 24   | 人称 · 标题形式      | 人称 `b mod 4`（我、我们、你、无人称）；标题形式 `⌊b/4⌋ mod 6`                                        |
| 25   | 句长 · 语域          | `3 + (b & 15)` 个词；语域 `(b >> 4)/15`（0 口语 … 1 正式）                                            |
| 26   | 变数对象             | 9 个对象（减去场景移除的）中 `b mod n`                                                                |
| 27   | 变数操作 · 量        | 10 种操作（减去场景移除的）中 `b mod n`；量 `⌊b/10⌋`                                                  |
| 28   | 场景格式             | 场景格式中 `b mod n`；仅非 web 场景                                                                   |
| 29   | 中文标题字体         | `b mod 14`（中文页面使用）                                                                            |
| 30   | 等宽字体             | `b mod 8`                                                                                             |
| 31   | —                    | 不使用（web 场景下 28 也不使用）；两者都记录在映射过程里                                              |

表格放不下的几个公式：

- **文本块（字节 13）。** `span = max(min(2, columns), round(columns × (0.35 + 0.65 × (b & 15)/15)))`，`start = 1 + round((columns − span) × (b >> 4)/15)`。文本块总在栅格内。
- **缓动（字节 23，b ≥ 32）。** `cubic-bezier(((b >> 2) & 7)/7 × 0.9, (b >> 5)/7 × 1.4, (b & 3)/3 × 0.8 + 0.1, 1)`。
- **时长（字节 22）** 取整到 10 ms；可能是 0 ms，表示变化瞬间完成。
- **变数的量（字节 27）** 按操作解读：旋转 `2 + 量 × 0.5°`，放大到 `2 + 量 × 0.1` 倍，缩小到 `0.6 − 量 × 0.012` 倍，重复 `2 + 量 mod 4` 次，偏离栅格 `1 + 量 mod 3` 列；其他操作不用它。
- **中文正文字体**不占字节：正文字体回退为衬线时用 Noto Serif SC，否则用 Noto Sans SC。
- **标题字重**取自所选标题字体在 Google Fonts 上真实存在的字重，所以一定能加载。

少数值还依赖另一个字节：字重（字节 8 在字节 6 选出的字体的字重里取）、文本块（字节 13 按字节 12 的列数解读）、列间距和母题尺寸（字节 11 的密度单位的倍数），以及中文正文字体（字节 7）。`mapping.test.ts` 逐个翻转每个字节，检查映射过程里其他行都不动。

## 4. 配色

配色是算出来的，不是查表。字节 0–5 决定色相、深浅、纸的明度和彩度、强调色彩度和第二强调色的色相偏移；然后每个文字颜色的明度都是**解出来的**：从纸色出发，按 OKLCH 明度每步 0.005 往远离纸色的方向走，直到满足对比度下限：

| 颜色      | 由什么构成                                    | 与纸色的对比度 |
| --------- | --------------------------------------------- | -------------- |
| `paper`   | 明度和彩度来自字节 2–3，色相来自字节 0–1      | —              |
| `ink`     | 同一色相，彩度 `min(0.035, 纸的彩度 + 0.012)` | ≥ 7.5          |
| `muted`   | 同一色相，彩度 0.02                           | ≥ 4.6          |
| `accent`  | 同一色相，彩度来自字节 4                      | ≥ 3.2          |
| `accent2` | 色相 + 字节 5 的偏移，彩度为强调色的 0.9 倍   | ≥ 3.0          |
| `rule`    | 纸的明度 ∓ 0.17，比纸稍多一点彩度             | —              |
| `panel`   | 纸的明度 − 0.045（浅色）或 + 0.05（深色）     | —              |

超出 sRGB 的颜色会降低彩度直到能显示，色相永远不变。字节 2 的 256 个取值里有 77 个给出深色纸，所以大约 30% 的哈希是深色。

## 5. 密度

字节 11 给出一个位置 `t`，从 0（疏朗）到 1（紧凑）。每个密度值都是 `t` 的线性函数：

| 值       | 公式                        | t = 0   | t = 1   |
| -------- | --------------------------- | ------- | ------- |
| 基础字号 | `18 − 4t` px，取到 0.5      | 18 px   | 14 px   |
| 行高     | `1.65 − 0.3t`               | 1.65    | 1.35    |
| 间距单位 | `10 − 6t` px，取整          | 10 px   | 4 px    |
| 区块间距 | `168 − 136t` px，取整       | 168 px  | 32 px   |
| 最大宽度 | `1080 + 360t` px，取整到 10 | 1080 px | 1440 px |

场景会收窄 `t` 的范围（§7）。

## 6. 约束

约束在读取任何字节之前生效。它们是设计身份的一部分：同一个哈希配不同约束就是不同的设计；要复现时，必须给 `get_brief` / `hash-design brief` 传同样的约束。

| MCP 参数         | CLI 参数           | 效果                                                                                                |
| ---------------- | ------------------ | --------------------------------------------------------------------------------------------------- |
| `light_only`     | `--light-only`     | 浅色纸；字节 2 按全范围读作明度，`0.90 + b/255 × 0.085`                                             |
| `dark_only`      | `--dark-only`      | 深色纸；字节 2 按全范围读作明度，`0.14 + b/255 × 0.12`                                              |
| `reduced_motion` | `--reduced-motion` | 无动效：时长 0，缓动 `none`（字节 22–23 记录在映射过程里但不生效）                                  |
| `brand_colors`   | `--brand <#hex>`   | 最多 2 个颜色：第一个替换 `accent`，彩度 ≥ 0.03 时还决定色相（字节 0–1 不用）；第二个替换 `accent2` |
| `scenario`       | `--scenario <id>`  | 要设计的东西：web（默认）、deck、app、dashboard、poster、email（[§7](#7-场景)）                     |

`light_only` 和 `dark_only` 不能同时使用。品牌色原样使用，它的对比度是多少就是多少：brief 的对比度表会如实列出。

## 7. 场景

`scenario` 说明要设计的是什么。它和其他约束一样：记录在 `roll.json` 和每份 brief 里，复现 ref 时要再传一次。数据在 [`packages/core/src/data/scenarios.ts`](../packages/core/src/data/scenarios.ts)，由 `packages/core/test/scenarios.test.ts` 覆盖。

| 场景          | 字节 28 选格式                                                               | 画布               | 密度 `t` 范围 | 基础字号            | 移除的变数对象 / 操作                   |
| ------------- | ---------------------------------------------------------------------------- | ------------------ | ------------- | ------------------- | --------------------------------------- |
| `web`（默认） | —（字节 28 不使用）                                                          | 响应式页面         | 0–1           | 密度基础字号        | —                                       |
| `deck`        | full-bleed · index-rail · document                                           | 1920×1080，固定    | 0–0.7         | 密度基础字号 × 2    | navigation、links / —                   |
| `app`         | tab-bar · top-tabs · single-flow · sheet                                     | 390×844 手机屏     | 0–0.7         | 限制在 16–17 px     | footer / —                              |
| `dashboard`   | sidebar · top-nav · wall                                                     | 1440×900 视口      | 0.3–1         | 限制在 13–15 px     | footer / —                              |
| `poster`      | portrait 1080×1350 · square 1080×1080 · story 1080×1920 · link-card 1200×630 | 格式尺寸，固定     | 0–1           | 密度基础字号 × 1.75 | navigation、links、footer / —           |
| `email`       | single-600 · banded-640 · digest                                             | 600 或 640 px 单栏 | 0–0.7         | 限制在 16–17 px     | navigation / vertical、rotate、off-grid |

字节如何作用：

- **不变。** 字节 0–10、12–25、29 和 30 的读法与 web 完全相同，所以一个哈希在每个场景下都保留它的颜色、字体、大小写、字距、字号比例、栅格、锚点、母题、材质和语气。换场景不换方向。
- **重新缩放。** 字节 11 映射到场景的 `t` 范围内，所以密度值（以及作为单位倍数的列间距和母题尺寸）可能与同一哈希的 web 设计不同。
- **过滤。** 对该场景没有意义的变数对象和操作在读取字节 26、27 之前移除；列表变短可能改变选中项。
- **替换。** `email` 是静态的：没有动效，与 `reduced_motion` 相同。
- **新增。** 字节 28 选出场景的格式。
- **派生。** 基础字号由密度的基础字号缩放或限制得到（见上表）。`--max-width` 变成格式宽度，固定画布再加上 `--canvas-width` / `--canvas-height`。

brief 会多一节 **场景 Scenario**：格式和画布、文件与结构约定、幻灯片 / 屏幕 / 画板的数量、版式与锚点与动效如何转换，以及场景规则和禁忌。有场景的 brief，`critique_page` 会增加对这些约定的静态检查（规则 `scenario-<id>`）。

`scenario: "web"` 会被规范化掉，所以 web 设计带不带它都一样。场景数据有自己的指纹，`scenarioFingerprint()` = `sha256(JSON.stringify({ ALGORITHM, SCENARIOS }))` 的前 12 位十六进制，当前为 `4b8c484cc50e`，作为 `scenario data` 写进每份非 web brief。

## 8. 可复现性与库指纹

一个设计是 `(哈希, 约束, 库)` 的纯函数（非 web 场景再加上场景数据）。同一个 ref + 同样的约束 + 同样的场景 → 同一份 brief，前提是指纹一致。每份 brief 和每个 `roll.json` 都记录：

- `algorithm`：`hash-design/v2`。只有字节分配或公式改变时才会变。
- `library`：`sha256(JSON.stringify({ ALGORITHM, 字体池, 原语列表, BYTE_MAP }))` 的前 12 位十六进制，当前为 `bd20321c36ab`。它覆盖字体池（[`data/fonts.ts`](../packages/core/src/data/fonts.ts)）、原语列表（[`data/space.ts`](../packages/core/src/data/space.ts)）和字节映射表。`mapping.test.ts` 钉住了这个值，所以改动其中任何一项都是看得见、有意为之的改动。

改动列表会改变指纹：旧 ref 仍然能解析，但可能映射到不同的设计，所以请用指纹相符的 hash-design 版本复现旧 ref。

## 10. 与 `hash-design/v1` 的区别

`hash-design/v1` 用字节 0–1 从 40 个手写的流派"分支"（分属六个家族）里选一个，再用字节 2–13 在该分支的 3 套版式、字体对、配色等之间选择，并用碰撞探测（`<hash>+<probe>` 形式的 ref）让同一次掷骰的分支和家族彼此错开。所以一个方向等于 40 种有名字的风格之一，加上少量变化。

v2 把这一层完全删掉了：没有分支、没有家族、没有流派名、没有碰撞探测、没有 `+probe` ref，没有 `families` / `include_branches` / `exclude_branches` 约束，也没有 `list_branches` / `get_branch` 工具。每个字节直接驱动一个参数，所以设计空间是上面这些参数的乘积，而不是 40 种风格。v1 ref 在 v2 下无法复现；`parseRef` 遇到 `<hash>+<n>` 会报错并说明原因。[`examples/`](../examples) 下的四个示例是用 v1 做的，作为真实运行的记录保留（见各自的 README）。

## 11. 修改映射

- 增删一个字体或列表项会改变指纹（以及一部分哈希映射到的结果）。请在同一个提交里更新 `mapping.test.ts` 中钉住的值；改完字体池后运行 `node scripts/verify-fonts.mjs`（检查每个字体在 Google Fonts 上都能解析）。
- 改变哪个字节驱动哪个参数，或改动任何公式，都属于算法变更，必须提升 `ALGORITHM`（例如改成 `hash-design/v3`）。
